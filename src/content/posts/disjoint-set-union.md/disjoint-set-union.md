# 并查集的基本结构

并查集（Disjoint Set Union，简称 DSU）是一种用于维护若干个 **不相交集合** 的数据结构，主要用于解决 “元素分组” 以及 “分组关系动态变化” 的问题。在实际应用中，我们经常会遇到这样一类需求：系统中存在大量元素，这些元素会随着操作不断地被合并到同一个集合中，同时又需要频繁判断任意两个元素是否属于同一集合。若采用朴素的数据结构来维护这些关系，往往会导致实现复杂、效率低下，而并查集正是为了解决这一类问题而设计的一种高效数据结构。

从实现角度来看，并查集并不是直接存储每个集合中包含了哪些元素，而是通过维护元素之间的 “从属关系” ，间接刻画集合的划分状态。通过合理的数据组织方式，并查集能够在接近常数时间复杂度的情况下完成集合的查询与合并操作，因此在算法竞赛、图论算法以及工程实践中都有着极为广泛的应用。

在并查集中，我们需要用代码实现这样一个集合系统，它主要支持两种基本操作。第一种操作是 **查找操作** ，用于确定某一个节点当前属于哪一个集合；通过查找操作，我们可以判断两个节点是否处于同一个集合之中，这是并查集最核心、也是最基础的功能之一。只要能够准确地完成查找操作，集合的划分状态就能够被正确地反映出来。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作1.jpg)

第二种操作是 **合并操作** ，用于将两个节点所在的集合合并为一个新的集合。需要注意的是，合并操作并不是简单地将两个节点直接连接起来，而是将它们各自所属的整个集合进行合并，使得合并后这两个集合中的所有节点都被视为处于同一个集合中。合并操作会改变集合的整体结构，因此如何在保证正确性的前提下高效地完成合并，是并查集设计中的一个关键问题。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作2.jpg)

为了高效地实现这两种操作，并查集通常采用 **树型结构** 来表示集合。具体来说，每一个集合都可以表示为一棵树，树中的每一个节点对应一个元素，而不同的集合则对应不同的树。这样一来，所有集合整体上就构成了一片森林。通过这种表示方式，我们可以利用树结构天然的层次关系来组织集合中的元素，从而为后续的查找与合并操作提供清晰的结构基础。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作3.jpg)

当使用树型结构表示集合时，一个重要的约定是：**用树的根节点来代表整个集合** 。也就是说，同一棵树中的所有节点都属于同一个集合，而该集合的 “编号” 或 “代表元素” 就是这棵树的根节点。只要两个节点最终指向的是同一个根节点，就可以断定它们属于同一个集合。通过这种方式，集合之间的判定问题被自然地转化为根节点是否相同的问题，大大简化了判断逻辑。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作4.jpg)

为了实现查找操作，我们需要为每一个节点维护一个指向其父节点的指针。在这种表示方式中，**非根节点指向自己的父节点，而根节点则指向自身** ，以此作为根节点的判定条件。当我们从某个节点出发，沿着父节点指针不断向上追溯时，最终一定会到达一个指向自身的节点，该节点就是当前节点所属集合的根节点。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作5.jpg)

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作6.jpg)

在具体实现时，我们通常使用一个一维数组 `p` 来存储并查集的结构关系。数组的下标表示节点编号，而数组中对应位置存放的值则表示该节点的父节点编号。通过这种数组表示方式，原本抽象的树结构被压缩成了一种紧凑而高效的存储形式，既便于快速访问，又方便在合并操作中进行修改。

对于根节点而言，其父节点编号等于自身编号，这一点可以作为判断节点是否为根节点的依据；而对于非根节点，其父节点编号则指向树中更高一层的节点。通过不断访问 `p[x]` ，我们就能够逐步向上移动，最终定位到根节点，从而完成查找操作。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作7.jpg)

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作8.jpg)

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作9.jpg)

对于合并操作而言，其基本思想也十分直观：只需要找到两个集合各自的根节点，然后让其中一个集合的根节点指向另一个集合的根节点即可。通过这种方式，原本两棵独立的树就会被合并为一棵树，从而实现集合的合并。在最基础的并查集中，这种连接方式并不要求特定的顺序，只要保证连接的是根节点即可完成合并。

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作10.jpg)

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作11.jpg)

![基本操作图像](src\content\posts\disjoint-set-union.md\基本操作12.jpg)

通过上述结构设计，并查集成功地将集合关系转化为一组父子指针的维护问题，使得 “集合的表示” 与 “操作的实现” 都变得清晰而统一。在此基础之上，我们就可以进一步引入 **路径压缩** 、**按秩合并** 等优化策略，以显著降低树的高度，从而大幅提升并查集在大规模数据场景下的运行效率，为后续更复杂的应用与算法分析奠定坚实基础。

## 路径压缩

在并查集的基本实现中，查找操作是最为频繁的一类操作。如果仅使用最朴素的树结构来维护集合关系，那么在极端情况下，树的高度可能会不断增长，导致一次查找操作需要沿着父节点指针逐层向上追溯，时间复杂度接近线性。这显然会成为性能瓶颈。因此，在并查集的实际实现中，通常会对查找操作进行优化，其中最重要、也是最常用的一种优化策略就是 **路径压缩（Path Compression）**。

我们首先来看一下查找操作的完整代码及其执行过程。这里采用的是一种 **递归式写法**：从当前节点开始，如果该节点不是根节点，就递归地对其父节点执行查找操作，直到最终找到根节点为止。

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩1.jpg)

在上述基础写法中，查找操作虽然能够正确返回集合的根节点，但它并不会改变并查集原有的树结构。也就是说，如果某条查找路径较长，那么之后每一次对这条路径上的节点进行查找时，仍然需要重复经历同样的追溯过程。

为了解决这一问题，我们可以在查找操作中引入一个非常关键、但改动极小的优化。具体来说，只需要将递归函数中的 `return Find(p[x])` 替换为 `return p[x] = Find(p[x])` 。这一改动的含义在于：**在递归返回的过程中，将当前节点的父节点直接修改为集合的根节点** 。也就是说，函数在完成查找任务的同时，顺便对树的结构进行了调整。

为了更直观地理解这一过程，我们结合具体的执行流程来分析。当对某个节点执行查找操作时，递归调用会沿着父节点指针逐层向上，形成一条完整的查找路径；而当递归开始回溯时，每一层返回都会将当前节点的父节点更新为最终找到的根节点。这样一来，原本较长的查找路径就会被 “拉直” ，所有节点都被直接连接到根节点之下。

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩2.jpg)

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩3.jpg)

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩4.jpg)

经过一次查找操作后，这条路径上的节点层次关系会发生显著变化。原本需要沿着父节点指针逐层向上、经过多次跳转才能到达根节点的树形结构，会在路径压缩的作用下被整体“拉直”，路径上的各个节点都会被直接连接到集合的根节点之下，从而使原本较深的查找路径转化为一条高度极低的结构。这种调整并不会改变集合之间的从属关系，却能够有效减少后续查找过程中所需的指针跳转次数，使查找操作的平均开销显著降低。

最终的效果如图所示：原本层次较深、结构相对分散的树形路径被压缩为高度为 2 的紧凑结构。此后，无论从该路径上的哪一个节点开始执行查找操作，都只需经过极少的父节点跳转即可直接到达根节点，查找过程几乎退化为常数时间，从而为并查集在大量连续操作下保持高效性能提供了有力保障。

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩5.jpg)

![路径压缩图像](src\content\posts\disjoint-set-union.md\路径压缩6.jpg)

需要强调的是，路径压缩并不会改变并查集所表示的集合划分结果，它仅仅是对内部结构进行了一次等价变换，从而换取更高的运行效率。配合后续将要介绍的 **按秩合并** 等策略，路径压缩能够使并查集在理论与实践中都表现出极为优秀的性能，其单次操作的均摊时间复杂度可以认为接近常数。

## 按秩合并

下面我们来看一下并查集中 **合并操作** 的完整过程以及对应的实现思想。一次合并操作通常可以分为两个相互衔接的步骤：首先，通过查找操作分别找到两个节点当前所在集合的根节点，以此确定它们各自所属的集合；随后，再将这两个集合合并为一个新的集合。需要注意的是，合并操作的核心并不在于 “连哪两个节点” ，而在于 “以哪一个根节点作为新的集合代表” 。不同的合并方式，会直接影响合并后集合所对应树结构的高度，而树的高度又会进一步影响后续查找操作所需的时间成本。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并1.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并2.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并3.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并4.jpg)

从直观角度来看，如果在合并两个集合时，将 **高度较高的集合合并到高度较低的集合之下** ，那么合并后形成的新集合，其高度往往会在原有基础上继续增加；相反，如果将高度较低的集合合并到高度较高的集合之下，则通常不会引入额外的高度增长，更有利于保持整体树结构的扁平化。因此为了尽可能避免集合树 “长高” ，在合并操作中有意识地选择合并方向，就成为一种自然且有效的优化思路。

基于这一观察，我们可以采用 **按高度合并** 的策略：在合并两个集合时，比较它们根节点所对应树的高度，将高度较小的集合挂到高度较大的集合之下。这样一来，若两个集合的高度不同，则合并完成后，新集合的高度保持不变，从结构上避免了不必要的高度增长。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并5.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并6.jpg)

如果两个集合的高度恰好相同，那么无论将哪一个集合挂到另一个集合之下，合并后集合的高度都不可避免地会增加 1。在这种情况下，可以任意选择一个集合作为新的根节点。按照上述规则实现的合并策略，通常被称为 **按秩合并** ，其中 “秩” 并不一定严格等同于树的真实高度，而是作为一种用于指导合并方向的近似度量。其对应的完整实现代码如下所示。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并8.jpg)

需要特别注意的是，当查找操作中引入了 **路径压缩** 优化之后，集合中节点的父子关系会在查找过程中被动态调整，此时我们所维护的 “高度” 信息已经不再反映树的真实高度，而更像是一个历史意义上的参考值，仅用于在合并时给出一个大致合理的方向。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并9.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并10.jpg)

但这并不意味着按高度合并在引入路径压缩后就失去了意义。实际上，即使秩不再精确，只要合并方向在整体上是合理的，按秩合并依然能够有效抑制树高度的增长，与路径压缩相互配合，在实践中表现出极高的效率。

除了按高度合并之外，还可以采用 **按集合大小合并** 的策略，即在合并两个集合时，将元素个数较少的集合合并到元素个数较多的集合之下。与高度不同的是，路径压缩只会改变节点之间的连接关系，并不会影响集合中元素的真实数量，因此集合大小始终是一个准确且稳定的衡量指标。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并11.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并12.jpg)

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并13.jpg)

不过，按集合大小合并也并非完美无缺。在某些特殊情况下，可能会出现 **元素数量较少但树高度反而较高** 的集合被保留下来的情况，从而在合并之后使整体集合树的高度有所增加，这说明集合大小与集合高度之间并不存在严格的一一对应关系。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并14.jpg)

总体来看，无论是按高度合并还是按集合大小合并，都是非常优秀且实用的合并策略。当它们与路径压缩结合使用时，并查集的查找与合并操作在理论分析与实际运行中都表现出极高的效率。其时间复杂度通常可以用 **反阿克曼函数** 来描述，在人类可实现的计算规模范围内，该函数的取值几乎不会超过 4，因此在实际应用中，完全可以将并查集的操作复杂度近似视为 $O(1)$ 。

![按秩合并图像](src\content\posts\disjoint-set-union.md\按秩合并15.jpg)

## 深度优化

在前面的实现中，我们通常会额外维护一个 **高度数组** 或 **大小数组** ，用来辅助按秩合并或按集合大小合并。事实上，这些信息完全可以合并进并查集最核心的 `p` 数组中，从而进一步简化数据结构的设计。

具体来说，我们可以约定：**对于集合的根节点，`p` 数组中不再存储父节点编号，而是存储一个负数，用来表示该集合的高度或大小** ，而对于普通节点，`p[x]` 仍然表示其父节点的下标。通过这种方式，只使用一个数组就能同时维护父子关系与集合信息。

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化1.jpg)

在这种设计下，判断一个节点是否为根节点的方式也随之发生变化。由于根节点不再满足 “父节点指向自身” 的条件，而是通过一个负数来标识，因此在查询操作中，需要将原本的判断逻辑修改为：当 `p[x] < 0` 时，说明 `x` 是当前集合的根节点；否则，`p[x]` 表示它的父节点编号。

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化2.jpg)

需要特别注意的是，在使用负数存储高度或大小时，其数值含义与直觉正好相反。无论是按高度合并还是按集合大小合并，**负数的绝对值越大，表示集合越高或元素数量越多** ，也就是说，数值 “越小” 的负数反而代表 “越大” 的集合。因此在按高度合并的实现中，当两个集合高度相同时，高度的更新应当是减 1 而不是加 1。

同时，在按集合大小合并的实现中，也要注意更新顺序的问题。合并时应当先确定新的根节点，并将两个集合的大小相加，再将结果赋值给新的根节点；若顺序处理不当，很容易导致集合大小统计出错。

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化3.jpg)

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化4.jpg)

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化5.jpg)

![深度优化图像](src\content\posts\disjoint-set-union.md\深度优化6.jpg)

通过这种 “深度优化” 的方式，并查集在保持功能完整的同时，进一步减少了辅助数组的数量，使整体实现更加紧凑、统一。该写法在竞赛和工程实践中都非常常见，也可以看作是并查集的一种标准实现形式。当它与路径压缩以及合理的合并策略结合使用时，既能保证极高的运行效率，又能显著降低实现与维护的复杂度。
